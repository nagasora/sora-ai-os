# Implementation Harness

実装を止めずに前へ進めるための、最小変更・最小検証・PR handoff の運用ルール。プロジェクト固有の指示、ユーザーの明示要件、CIや安全性の必須条件が優先される。

## Start gate

着手前に、次の4点を短く確定する。小さな修正では1〜4行でよく、長い設計書は作らない。

- Scope: 今回変える機能とファイルの範囲
- Done: ユーザーが確認できる完了条件
- Test: 使い回す既存テスト、または追加する最小のテスト単位
- Out of scope: 今回は触らない改善

関連ファイルと既存テストを先に読み、最も近い既存の実装・fixture・テストを拡張する。曖昧さが実装を安全に変える場合だけ、必要な質問をする。

## Minimal implementation

- まず動く最小の本線を実装し、同じ変更内で不要な全面整理をしない。
- 既存の責務境界、依存、命名、エラー方針を優先する。
- 将来の拡張だけを理由に抽象化しない。フォールバック、リトライ、広い例外捕捉、互換層、機能無効化で本線の不具合を隠さない。
- 既存の未コミット変更を上書き・混入させない。差分を確認し、自分のファイルだけを扱う。

## Test budget

「1機能1テスト単位」をデフォルトにする。ここでいう単位は、既存テストファイル内の1つの再利用可能なテスト関数・パラメータ化ケース、または機能に対応する1つのテストファイルのいずれかである。

1. 既存テストを拡張・パラメータ化する。
2. 新しいテストファイルは、既存の配置では振る舞いを自然に表せない場合だけ作る。
3. 新しい外部から見える振る舞い、再発バグ、または実質的なリスク境界だけをテストする。
4. 内部実装の行・分岐、単純な委譲、名前変更・整形・文言だけの変更に、重複テストを追加しない。
5. まず対象テストを1回実行する。成功し、下記のリスク条件に該当しなければ検証を打ち切る。

次の場合だけ、関連する広い検証を追加する。

- 複数モジュール、公開API、データスキーマ・マイグレーションを横断する
- 並行性、認証・権限、セキュリティ、永続化、ビルド・配布に影響する
- CI、プロジェクト固有規約、ユーザー要件が要求する

バグ修正では、再現ケースを既存テストへ最小限追加し、原因を本線で直す。テストが通った後に「念のため」のテスト行列を増やさない。

## Stop and handoff gate

対象テストと必要な検証が通ったら、次の順で完了処理を行う。

1. 差分、対象ファイル、不要な変更、`git diff --check` を確認する。
2. 必要なドキュメントだけ更新し、無関係なリファクタリングを残さない。
3. GitHubのリモートがある変更は、ブランチへコミット・プッシュし、必ずPull Requestを開く。
4. PR本文に目的、変更概要、実行した検証、既知の制約を記載する。レビュー待ちやマージはユーザーが求めた場合だけ行う。

PR URLを取得できない場合は完了とせず、`BLOCKED` として不足しているリモート・認証・権限を明示する。GitHubではないリポジトリは、同等のレビュー可能なリンクがある場合だけその事実を記録する。

## Completion report

最終報告は次の情報に絞る。

```text
Status: PR opened / BLOCKED
Change: <何を変えたか>
Validation: <対象テストと必要な検証>
Test budget: <既存テストを再利用したか、新規単位はいくつか>
PR: <URL またはブロッカー>
Remaining: <既知の制約。なければ none>
```
